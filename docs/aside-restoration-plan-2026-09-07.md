# Aside 복원 실행 계획서 — 2026-09-07

상태: **PLAN_REVIEWED / 원본 기준 스냅샷·소스 차이 목록 작성 / 제품 구현 미착수**.

이 문서의 최초 산출물은 계획서다. 이후 사용자가 승인한 원본 구성 고정·차이 목록 작업은 [후속 보고서](aside-restoration-baseline-and-differences-2026-09-07.md)에 기록했다. 구현, 서비스 재시작, 계정 변경, Chromium 빌드는 수행하지 않았다.

진행 상태: P0는 기준 스냅샷을 확보했으나 확장 실제 실행·현재 화면 조건 확인이 남아 엄격 합격은 보류다. P1은 선언한 파일 보존 범위를 독립 검증했고 전체 동적 의존성은 미확인이다. P2는 소스 차이 목록을 작성했으며 모든 실행 경로의 동작 대조는 남았다. P3 이후는 미착수다. 아래 합격 기준을 낮추지 않는다.

디자인 차이의 원인, native/extension 수정 경계, V00–V08 순서와 화면 합격 기준은 [Chromium 디자인 복원 계획](aside-chromium-design-restoration-plan-2026-09-07.md)에 구체화했다. 해당 문서도 검토·계획 산출물이며 제품 구현 완료를 뜻하지 않는다.

## 1. 목표와 복원 기준

**그대로 가져올 수 있는 배포 코드는 원문 그대로 보존하고, 우리가 바꾼 연결을 추적한 뒤, 네이티브 기능은 원본과 비교하면서 복원한다.**

사용자가 체감할 목표는 같은 입력과 조건에서 필요한 페이지를 읽고, 올바른 도구를 실행하며, 결과와 작업 상태를 원본에 대응하게 표시하는 것이다. 조사 대상은 `belmont-browse`의 Aside 브라우저·확장·데몬·연결 코드다. Belmont Electron 앱 전체의 복원 완료를 이 계획으로 선언하지 않는다.

‘100%’는 다음과 같이 제한해서 쓴다.

| 구분 | 목표 | 완료를 증명하는 방법 |
| --- | --- | --- |
| 배포 원문 | 동봉된 JS·HTML·CSS·이미지·폰트·내장 지침·설정·스키마를 정확히 확보 | 고정한 배포 구성의 파일 목록, 컨테이너 경계, 길이·해시·추출 바이트 일치 |
| 공개 소스 | 대응 리비전의 Chromium 및 공개 의존성 확보 | 원본 메타데이터와 revision·의존성·빌드 설정 대조. Aside 전용 수정은 별도 |
| 네이티브 재구현 | 창·탭·비공개 API 등 원본에서 관측한 기능과 상태 전이 재현 | 기능별 입출력·이벤트·실제 화면·수명 검증. 원래 C++ 소스 원문 복원이라고 부르지 않음 |
| 외부 서비스 | 원본 연결 가능 여부와 대체 구현의 차이를 명시 | 실제 호출 경로와 응답 계약 관측. 설치물에 없는 서버 소스·모델 가중치 복원을 약속하지 않음 |

소스맵이나 원래 TS/JSX/C++ 소스를 추가 확보하면 원문 복원 범위를 넓힐 수 있다. 바이너리 크기, 함수명 개수, 스키마 일치, 테스트 개수를 합쳐 ‘제품 전체 복원율’을 만들지 않는다.

## 2. 계획 작성 시점의 출발 상태와 보존 대상

근거 구분: `direct_observation`은 현재 읽은 파일·프로세스, `raw_recompute`는 원시 바이트 재계산, `documented_prior_claim`은 이전 실행 기록, `inference`는 해석, `unverified`는 미확인이다.

| 항목 | 현재 근거와 해석 |
| --- | --- |
| 원본 VM | `direct_observation`: QEMU PID 7850 실행 중. 이번에는 guest 내부 상태를 새로 조회하지 않았다 |
| 원본 배포 구성 | `documented_prior_claim`: 앱 1.0.825.1, 실제 데몬 1.26.906.1714. 설치 후 갱신된 확장·컴포넌트는 P0에서 다시 고정 |
| 포크 기본 실행 | `direct_observation`: `run-fork.sh`는 Linux Chromium, 확장 manifest 1.26.824.2151, daemon engine 902를 선택. `serve.mjs`는 `openai-codex` provider를 구성 |
| 원문 보존 사례 | `raw_recompute`: 905 추출 JS 전체가 원본 실행파일의 연속 바이트와 일치. 전체 패키지의 모든 파일 검증 완료를 뜻하지 않음 |
| 지난 개선 | `documented_prior_claim`: 범위가 제한된 native·검색 검증 통과, 마지막 쇼핑은 PARTIAL. 사양·조건·배송·리뷰 근거와 초기 창 표시 문제가 남음 |
| 실행 중 비교 작업 | `direct_observation`: 지난 캠페인 status에 taskOwnedPids와 runningJobs가 비어 있음. 이번 프로세스 목록에도 해당 replay 실행 명령이 없음 |

보존 대상은 원본 VM, 로그인·프로필·세션 DB, 기존 증거, Orca 모바일 서비스, 현재 Chromium 작업 트리다. 현재 저장소의 무관한 변경 `source/host/extensions/transcript/transcript-manager.ts`, `docs/bot-training-plan-2026-09-06.md`, `scratch_macvm/`도 유지한다. PID는 식별 참고이며 이후 작업 시작 시 실행파일·명령·소유 관계를 다시 확인한다.

P0의 기존 원본 VM은 읽기 관측 기준으로 유지한다. P4/P6의 탭·세션·설정·프로필 변경 검사는 별도의 검증용 원본 환경과 포크 후보에서 수행한다. 고정한 배포 구성을 별도 설치하거나 일관성을 확인한 복제본을 사용하고, 테스트 계정·프로필·초기 상태의 소유권을 명시한다. 자원이 부족하면 별도 호스트/자원을 확보할 때까지 변경 검사를 미실행으로 남기며, 기존 VM을 끄거나 보호 프로필을 대신 사용하지 않는다.

이전 [복원 지도](../belmont-browse/aside-fork/usecases/RESTORATION-MAP-2026-09-06.md)의 ‘정체 미상=불가’는 이 계획에서 **미해결**로 취급한다. macOS 전용 구현은 **플랫폼 이식 대상**으로 취급한다. 원본 소스 원문의 미보유와 기능 구현의 불가능을 섞지 않는다. 기존 문서는 당시 기록으로 보존한다.

## 3. 먼저 고정할 검증 기준

복원 작업자가 아래 기준을 구현 결과에 맞춰 낮추지 않는다. 기준 변경은 이유·영향·기존 실패 사례를 기록하고 새 판으로 분리한다.

| 평가 축 | 필수 통과 조건 | 실패 시 처리 |
| --- | --- | --- |
| 원문과 출처 | 고정한 배포 구성에서 복원 대상으로 선언한 모든 파일이 출처·길이·해시로 연결되고, 누락·설명 없는 변조가 없음 | P1로 돌아가 재추출. 현재 패치본을 원본으로 등록하지 않음 |
| 실행 경로 | 실제 로드된 파일·설정·모델 입력·도구 등록과 실행 종료 상태를 연결. 바뀐 경로마다 이유와 차이 존재 | 해당 단계 미통과. UI 모델 이름이나 파일명만으로 일치 판정하지 않음 |
| 도구와 상태 | 고정 입력에서 반환 본문·오류·이벤트·파일/탭 효과·취소 의미가 계약에 부합 | 최초 차이를 재현하고 해당 경계부터 수정 |
| 사용자 기능 | 사전 등록한 필수 흐름을 실제 UI에서 수행하고, 근거·조건·완료 상태를 확인 | 관련 기능 PARTIAL 또는 UNVERIFIED. 다른 성공 사례로 상쇄하지 않음 |
| 재현성과 유지보수 | 보존 원문 + 공개 기준 소스 + 명시적 패치로 별도 작업본을 구성할 수 있고, 독립 검토가 원시 근거를 확인 | 패치 누락·수동 수정·관측 공백을 해결하기 전 완료 보류 |

전체 배포 원문 보존과 기능 검증은 별도 분모로 보고한다. 선언한 기능 목록의 미실행 항목을 분모에서 빼지 않는다. 표본 과제 합격은 해당 범위의 합격이며 모든 웹사이트·모든 모델 응답의 동일성은 아니다.

## 4. 단계별 실행 순서

### P0. 비교할 원본 구성부터 고정

- 현재 설치물의 앱·Framework·실제로 로드된 확장·데몬·native helper·갱신 컴포넌트 경로와 버전·해시를 읽는다. 설치 DMG에 든 버전과 실행 중 버전을 따로 기록한다.
- 기준 후보는 기존 원본 VM에서 관측한 구성이다. 906 구성의 실제 파일과 출처를 확보할 수 있는지 먼저 확인한다. 확보되지 않으면 기준 고정 실패로 남긴다.
- 905는 원문을 확보한 별도 비교 후보일 뿐이다. 905 포크와 906 원본을 ‘같은 버전’ 비교로 취급하지 않는다. 이전 배포 구성을 사용하려면 별도 원본 환경에서 검증해야 한다.
- 앱과 컴포넌트의 버전 숫자를 억지로 같게 만들지 않는다. 설치 manifest·업데이트 기록·실제 로드 경로로 **원본이 실제 사용한 조합**을 증명한다.
- OS·언어·시간대·창 크기·배율·프로필·로그인 여부·모델 provider/id/effort·추가 지침·사이트 지식을 기록한다. 원본과 포크의 의도적 차이는 명시한다.
- 관측 시작·종료의 파일 해시를 비교해 자동 업데이트 중 변동을 탐지한다. 기존 VM의 업데이터를 임의로 중지하거나 설정을 바꾸지 않는다.

산출물: `baseline-manifest.json`, `runtime-observation.json`, `environment-differences.md`.

합격: 구성요소별 실제 로드 대상과 원본 출처가 연결되고, 관측 중 버전 변동이 없거나 변동 전후를 분리했다. 하나라도 불명확하면 P0는 미완료다.

### P1. 원본을 손대지 않는 보관소와 복원 목록 작성

- 설치 컨테이너와 각 멤버를 원문으로 보관한다. 파일 경로·종류·길이·해시·symlink·실행 모드와 추출 도구/명령을 기록한다.
- SEA의 JS, CRX/ZIP 확장, PAK 리소스, 동봉 skills·프롬프트·스키마·native 모듈을 구분한다. 직접 동봉되지 않은 생성물과 원래 개발 소스는 별도 표시한다.
- 디스크 크기만 보고 일부를 생략하지 않는다. 파일 목록과 실제 로드/동적 import 대상을 연결하여 비교 구성에서 필요한 리소스 누락을 찾는다.
- 공개 Chromium revision, 의존성, `args.gn`, 컴파일러 정보를 기록한다. 현재 트리는 Git HEAD만으로 보존되지 않으므로 tracked diff·새 파일·overlay·패치 적용 순서를 함께 보관한다.
- 추출기는 컨테이너 길이·경계와 출력 바이트를 검사한다. 독립 검토자는 추출기를 재사용하지 않고 컨테이너의 원시 구간/멤버와 대조한다.
- `raw/` 원문과 `candidate/` 패치본을 분리한다. 원본을 찾지 못한 패치본은 `ORIGINAL_NOT_VERIFIED`로 표시한다.

산출물: `source-inventory.json`, `extraction-manifest.json`, `source-availability.md`, `patch-inventory.json`.

합격: 고정한 구성에서 선언한 배포 원문 대상의 누락과 설명 없는 차이가 0이다. 이것은 원래 TS/C++ 소스 전체 복원 판정이 아니다.

### P2. 포크가 원본을 바꾼 지점 전수 분류

우선 확인할 경로는 `belmont-browse/src/{core,session,serve,chrome,daemon-server,credentials,web-search,memory-search}.mjs`, `belmont-browse/tools/patch-daemon*.py`, `belmont-browse/aside-fork/`의 native overlay·patches, 런타임 지식 주입이다.

각 변경을 다음 다섯 가지로 분류한다.

1. 원본 그대로 사용하는 코드.
2. Linux·프로세스 연결에 필요한 이식 코드.
3. 원본의 기능·기본값·행동을 바꾼 코드.
4. 원본 서비스가 없어 별도로 대체한 코드.
5. 이유나 원본 대응이 불명확한 코드.

우선 대조할 것은 부분 bootstrap, 모델 provider 선택, `ASIDE_API_URL`, 로컬 검색/메모리 훅, 추가 AGENTS·사이트 지식, 설정 기본값, 화면 읽기 지침이다. 각 행에 원본 위치·포크 위치·변경 이유·영향 기능·실제 실행 증거·유지/수정/미결정을 붙인다.

산출물: `deviation-ledger.jsonl`, `prompt-and-settings-diff.json`, `external-service-contracts.md`.

합격: 현재 실행 경로의 모든 차이를 원문·이식·행동 변경·대체·미확인 중 하나로 설명한다. ‘Linux 때문’이라는 한 줄로 모든 변경을 정당화하지 않는다.

### P3. 원본 클라이언트 로직을 우선 복구하고 이식 코드를 분리

- 원본 JS를 기준으로 별도 실행 후보를 만든다. 원본 entrypoint와 전체 초기화 순서를 먼저 추적한다. 필요한 의존성을 복구하거나 플랫폼 경계에서 적응시키고, 설명 없이 내부 init 몇 개만 골라 호출하는 상태를 없앤다.
- 원본 내장 프롬프트·도구 목록·설정 기본값을 대조한다. 포크 전용 지침·사이트 지식은 독립적인 사용자 기능으로 분리하여 기준 비교에 조용히 섞이지 않게 한다.
- 실제 모델 요청에 전달되는 지침·도구 정의·설정 값을 관측한다. UI의 모델 선택 표시만 비교하지 않는다. 서버 내부 라우팅은 관측 불가라면 그대로 미검증이다.
- 네이티브 세션 생성 경로와 직접 API 경로를 모두 추적한다. 한쪽만 수정하고 다른 쪽의 권한·설정·지식 상속이 달라지는 것을 막는다.
- 현재 고친 크래시·숫자 입력·검색을 일괄 되돌리지 않는다. 격리 후보에서 원본 동작과 비교한 뒤 버그 수정인지 복원에 필요한 차이인지 기록한다. 원본의 결함을 개선했다면 명시적인 의도적 차이로 남긴다.
- 원본 서버 접근은 기존에 허용된 정상 계정·연결 범위에서 가능 여부를 확인한다. 불가능하면 해당 경로는 `EXTERNAL_UNAVAILABLE`로 남긴다. 로컬 검색/메모리는 대체 구현으로 표시하며 원본 동등성 판정을 승계하지 않는다.

산출물: 버전별 격리 후보, `adapter-contracts.md`, `initialization-trace.jsonl`, `actual-model-input-manifest.json`, 재현 가능한 증분 패치.

합격: 원본 클라이언트 로직을 건너뛰는 모든 경로와 플랫폼 적응의 차이가 설명되고, 아래 P4의 관련 계약 검사를 통과한다. 외부 접근 실패를 숨기는 자동 대체는 불합격이다.

### P4. 모델 판단을 빼고 도구·상태 계약부터 맞춤

- 같은 의미의 초기 상태와 고정된 도구 입력을 원본과 후보에 전달한다. 각 환경에서 생성된 ref·탭 ID를 대응시키며 다른 세션의 ref를 복사하지 않는다.
- 대응 실행마다 검증용 프로필·설정·메모리·사이트 지식·로그인 상태·캐시의 출발 상태를 기록한다. 복원 가능한 로컬 상태는 검증용 snapshot으로 되돌리고, 서버 상태나 사이트 응답처럼 되돌릴 수 없는 변화는 차이로 남긴다. 이전 실행의 학습/캐시 효과를 동일 조건이라고 숨기지 않는다.
- 비교 단위는 `입력 → 호출 → 실제 효과 → 반환 → 저장 상태 → 종료`다. 탭 열기·닫기, 입력·readback, 스크롤·캡처, 오류·취소·재시도·세션 종료를 포함한다.
- 화면 preview와 모델용 `details.contextContent`, 전체 출력 파일, 이미지 attachment를 각각 확인한다. 본문 잘림·인용 매핑·단위·조건·옵션을 잃지 않는지 검사한다.
- 도구 계약 비교에서는 검증된 테스트 페이지·동결 입력을 사용한다. 실사이트 비교는 P6로 분리한다. CAPTCHA·로그인 차단을 통과했다고 꾸미거나 모의 응답으로 실서비스 성공을 주장하지 않는다.
- ID·시각처럼 달라도 되는 필드는 사전에 목록으로 고정한다. 가격·단위·출처·옵션·오류·탭 소유권 등 의미 있는 차이를 정규화로 지우지 않는다.
- 결과 문자열이 같아도 실제 효과와 종료 상태가 다르면 실패다. 수집 누락은 0건이 아니라 `UNVERIFIED`로 기록한다.

산출물: `contracts/`, `raw/tool-traces/`, `normalized-diff.json`, `first-divergence.jsonl`.

합격: 사전 등록한 필수 계약에서 설명 없는 의미 차이가 0이다. 의도적 버그 수정·OS 차이·외부 미확인은 별도 목록에 남긴다.

### P5. 네이티브 기능을 기능 단위로 복원

- 기존 전용 API·UI 목록, 원본 문자열·리소스·역어셈블, 실제 화면, 새 실행 추적을 합쳐 기능 목록을 만든다. 기존 76개 구간이나 API 개수만으로 전체 범위를 고정하지 않는다.
- 우선순위 1: 초기 실행·온보딩 창 표시, 프로필/팝업 닫기 수명, 세션/탭 소유권, 완료·취소·복구 상태. 우선순위 2: 설정 저장/재시작, 탭·사이드바·입력·분할 화면. 나머지 원본 노출 기능은 목록에서 계속 추적한다.
- 구조·상수·이벤트 순서를 원본 근거에 연결한 다음 최소 범위로 수정한다. 수정한 파일은 증분 패치로 보존하고, 알려지지 않은 기준 소스에는 패치를 적용하지 않는다.
- macOS 전용 API는 사용자에게 보이는 기능과 반환 계약을 Linux 방식으로 대응시킨다. API 이름·OS 내부 구현이 같은 것처럼 표시하지 않는다.
- 미확인 구간은 호출자·참조 데이터·동적 관측·정확한 공개 기준선 순으로 좁힌다. 추가 분석 경로가 남아 있으면 `UNRESOLVED`다. 현재 방법의 실패를 불가능 판정으로 바꾸지 않는다.
- 빌드는 별도 output과 작업 잠금을 사용한다. 원본 VM이 사용하는 자원과 충돌하면 빌드를 미루거나 별도 자원을 사용한다. 현재 VM 종료를 빌드의 전제로 삼지 않는다.

산출물: `feature-matrix.csv`, `native/patches/`, `native/raw/`, 실제 UI 캡처와 관측 기록.

합격: 필수 기능마다 원본 근거·구현 위치·실제 실행 증거가 연결되고, 회귀와 독립 검토를 통과한다. 화면을 찍기만 하고 보지 않은 검사는 완료가 아니다.

### P6. 실제 업무와 새 과제로 최종 비교

필수 흐름은 다음을 포함하며, P0/P2의 전체 기능 목록에서 누락된 노출 기능을 추가한다.

| 흐름 | 반드시 확인할 것 |
| --- | --- |
| 최초 실행·기존 프로필 | 초기 창이 보이고 작업 시작 가능. 수동 구조 작업이 필요하면 기록하고 실패 처리 |
| 검색·문서 읽기 | 검색 링크·인용·실제 본문·시각 근거·조건 보존. 스니펫을 본문으로 취급하지 않음 |
| 복잡한 상품 비교 | 상세·본품 옵션·조건부 가격·배송·리뷰·이미지 사양. 없는 근거는 미확인으로 표시 |
| 세션·탭 분리 | 두 작업의 탭·파일 효과·종료 소유권, 다른 채팅 탭 보존 |
| 취소·실패·복구 | 모델·도구 중단, pending 상태 해소, 재개 후 중복 실행 여부 |
| 설정·프로필·수명 | 설정 지속, 프로필 전환, 팝업 닫기, 부모 창 종료와 알림 처리 |

- 기존 C/D/E는 회귀 사례다. 별도로 새로운 사이트/과제를 독립 검토자가 선정해 동결하고, 구현자는 해당 결과를 보기 전에 변경을 마친다.
- 실제 업무 비교는 같은 요청·관측 가능한 모델 설정·동등한 프로필 조건을 사용한다. OS·계정·사이트 응답·하위 에이전트 모델 차이는 기록한다. 문장이나 클릭 순서의 완전 일치를 요구하지 않고 요청 충족과 근거·행동 제약을 평가한다.
- 원본도 사이트에서 차단되면 그 사례는 차단 관측이다. 성공률을 꾸미기 위해 다른 과제로 교체하지 않으며, 별도 접근 가능한 사례의 결과도 분리한다.
- 엄격한 파일 변경 금지 과제에서는 원본/포크의 operational tmp 쓰기도 실제 결과로 센다. 프로젝트 파일 불변과 파일 변경 0은 다른 조건이다.
- 반복 수는 P6 시작 전에 고정한다. 각 필수 실업무 유형은 원본/후보 대응 실행 3쌍을 초기 예산으로 제안하며, 성공·실패·차단·관측 공백을 전부 남긴다. 새 과제는 결과 확인 뒤 튜닝에 사용하지 않는다.
- 새 과제에서 드러난 결함을 수정하려면 해당 과제를 회귀 사례로 전환한다. 수정 후 최종 평가에는 독립 검토자가 새로 동결한 미열람 과제를 사용한다. 이전 실패와 소비한 예산을 보존하며, 새 과제 선정으로 실패를 삭제하지 않는다. 추가 평가 예산이 없으면 최종 검증 대기로 남긴다.

산출물: `acceptance-prereg.json`, `raw/real-tasks/`, `adversarial/`, `acceptance-report.md`.

합격: 필수 항목별 판정이 모두 존재하고 통과 범위에 미확인 필드를 섞지 않았다. 필수 항목에 실패·차단·관측 공백이 남으면 전체 범위 합격을 선언하지 않는다. 독립 검토 결과와 원시 근거를 주 담당자가 재확인한다.

### P7. 재현 가능한 배포 후보와 인수인계

- 원문·공개 기준 소스·명시적 패치·환경 설정 목록만으로 별도 작업본을 다시 구성한다. 개인 작업 트리에만 남은 파일이 없는지 확인한다.
- `Browser.pdl`을 포함한 overlay와 새 파일, 패치 순서, 실제 실행 바이너리 해시를 연결한다. 기존 전체 패치 파일을 현재 전체 상태라고 가정하지 않는다.
- 복원 결과는 `원문 보존 / 이식 완료 / 의도적 변경 / 대체 구현 / 외부 미확인 / 미해결`로 따로 보고한다.
- 후보 설치/전환과 기존 서비스 재시작은 별도 실행 단계다. 검증된 변경 목록·되돌리기 절차·열린 결정을 먼저 제시한다. 현재 계획서 작성이 해당 전환을 승인한 것은 아니다.

산출물: `REPRODUCE.md`, `FINAL-REPORT.md`, `HANDOFF.md`, candidate manifest.

합격: 별도 작업본 재구성 및 필요한 검사·렌더 관측이 통과하고, 원시 근거·남은 차이·실행 중 작업 소유권이 인수인계에 남는다. 최종 candidate manifest의 실행파일·bundle·패치·설정 해시를 P4/P6의 실행 manifest와 연결한다. 재구성 결과가 달라지면 변경 영향에 해당하는 계약·실업무 검증을 다시 수행하며, 이전 결과를 자동 승계하지 않는다.

## 5. 작업별 역할과 반복 예산

- 주 담당자: 상태·범위·원본 구성 고정, 변경 결정, 원시 근거 확인, 최종 판정.
- 추출/연결 담당: P1~P4의 지정 파일만 작업. native 담당과 소유 경계를 분리한다.
- native 담당: P5의 지정 기능과 파일만 작업. 다른 사람의 미커밋 변경을 되돌리지 않는다.
- 독립 검토자: 틀렸다는 가정으로 새 검사를 만들고, 원문 바이트·입출력·이미지를 다시 확인한다. 구현자의 추출기나 판정 함수를 정답으로 재사용하지 않으며 검증 대상을 수정하지 않는다.

선행 조건은 `P0 → P1 → P2 → P3/P4 반복 → P5/P4 반복 → P6 → P7`이다. 독립적인 추출·목록 작성·원시 검토만 병렬화한다. 검증 완료 전 여러 경계의 행동을 동시에 바꾸지 않는다.

예산은 구현 시작 전에 비용·자원 상태와 함께 동결한다. 기본 제안은 결함 하나당 서로 다른 근거를 반영한 수정 3회, 필수 실제 업무 유형당 대응 실행 3쌍이다. 같은 접근이 2회 실패하면 원인을 분해하고 더 좁은 재현을 만든다. 예산을 소진하면 최선 결과·각 수정의 효과·막힌 경계·다음 분석을 남긴다. `예산 소진`을 `복원 불가능`으로 표시하지 않는다.

## 6. 향후 산출물 배치

아래는 최초 계획 시점의 예정 구조다. 이후 구성·차이 조사용 `data/artifacts/aside-restoration_20260907T041632Z/`를 만들었으며, 실제 생성 범위는 [후속 보고서](aside-restoration-baseline-and-differences-2026-09-07.md)를 따른다. 구현 후보·계약 실행·replay 디렉터리는 아직 만들지 않았다.

```text
README.md / PREREG.md / status.json / checkpoint.json
baseline/                 원본 구성과 환경 관측
raw/                      변경하지 않은 원본 컨테이너·리소스·실행 증거
inventory/                원문·차이·기능 목록
candidate/                패치·플랫폼 적응이 들어간 별도 작업본
contracts/                고정 도구 입력과 허용 차이
replays/                  초기 상태·실행 명령·로그·결과·화면
adversarial/              독립 검토 코드와 원시 출력
FINAL-REPORT.md / HANDOFF.md
```

원본 계정 비밀값은 공유 문서/커밋에 복사하지 않는다. DB는 읽기 전용 관측 또는 일관된 backup을 사용하며 실행 중 DB/WAL을 무작정 복사한 결과로 상태 일치를 주장하지 않는다. 장기 작업에는 owner·명령·cwd·PID·heartbeat·로그·종료/복구 절차를 붙인다.

## 7. 실행 시작 시 첫 작업 묶음

1. 프로세스·자원·기존 변경 상태를 다시 읽고 보호 대상을 확인한다.
2. 원본 VM의 실제 앱·확장·데몬·컴포넌트 구성을 읽어 P0 manifest를 만든다.
3. 그 구성의 원문과 동적 의존성을 새 보관소로 추출하고 독립 바이트 대조를 한다.
4. 현재 포크와의 차이 목록을 만든다. 첫 구현 대상은 **원본 코드가 존재하는데 현재 연결·지침에서 달라진 경계** 중 실제 실패와 연결되는 항목으로 정한다.
5. 첫 변경 전에 해당 경계의 고정 입력/실제 효과 검사와 되돌리기 패치를 준비한다.

P0~P2를 끝내기 전에는 새 검색 알고리즘, 사이트별 정답 지침, 광범위한 네이티브 재작성을 시작하지 않는다. 먼저 원본과 갈라지는 위치를 증명한다.
