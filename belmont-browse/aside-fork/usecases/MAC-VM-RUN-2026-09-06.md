## 부검 — 왜 Haswell 로는 못 부팅했나 (원인 특정 완료)

증상: macOS Sonoma 설치 미디어가 애플 로고까지는 뜨는데 ~8초 만에 재시작을 반복. 설치 화면을 못 봤다.

기제(mechanism) 수준 사인:
- verbose 부팅(-v)을 OpenCore config.plist(boot-args)에 넣어 보니 boot.efi 가 커널캐시까지
  정상 로드하고 XNU 커널로 점프한 직후 화면이 꺼졌다. (Err(0xE) 줄들은 `.development`
  커널캐시가 없어 release 로 폴백하는 정상 로그. wake-failure 도 정상 콜드 부팅.)
- KVM ftrace(kvm_exit/kvm_entry/kvm_inj_exception)로 잡은 마지막 사건:
  - 커널이 자기 가상 주소(0xffffff80…)에서 실행 중 = XNU 가 초기화까지 꽤 진행함.
  - 전원 관리 MSR(0x198 IA32_PERF_STATUS, 0x199 PERF_CTL) 읽고 EFER(SCE) 켠 뒤
    `read_cr4` VMEXIT → 그로부터 ~385µs 뒤 `reason shutdown` (SVM 삼중 결함).
  - shutdown 의 intr_info=0x80000b08 → vector 0x08 = **#DF(이중 결함)**. 즉 게스트 내부에서
    이중 결함이 나 삼중 결함으로 번져 CPU 가 리셋.
  - `kvm_inj_exception` 개수 = 0 → KVM 이 주입한 예외가 아니라 게스트가 스스로 낸 결함.
- 판정: XNU 의 **XCPM(Haswell 이상 전원 관리) 초기화 경로**에서 이중 결함. 이 중첩 환경
  (Hyper-V → WSL2 KVM → macOS)에서 `read_cr4` 가 가로채이는 것 자체가 중첩 상태의 지문이고,
  그 직후 XCPM 코드가 결함을 낸다.
- 사망 반경: "Haswell-noTSX CPU 모델" 셀만 죽었다. rdrand/rdseed/fsgsbase 를 꺼도 같은 위치에서
  동일하게 죽어(이 셋은 원인 아님) 배제. 우주(맥 VM 자체)는 안 죽었다 — 아래.

원인 유도 재설계(성적표 튜닝 아님): CPU 모델을 **Penryn** 으로 바꿨다. Penryn 은 XCPM 대상
계열이 아니라 XNU 가 레거시 ACPI 전원 관리 경로를 타서 문제의 코드를 아예 건너뛴다. 소노마가
요구하는 AVX2/SSE4.2 는 `+avx2,+sse4.2` 로 강제로 얹었다(호스트에 있음, 실행됨). 결과:
복구 화면(Reinstall macOS Sonoma / Disk Utility 메뉴)까지 정상 도달. `boot.sh` 에 반영함
(백업: `boot.sh.bak-haswell`). OpenCore verbose 는 켠 채로 둠(백업: `OpenCore.qcow2.bak-verbose`).

## 2차 벽과 부검 — 설치된 OS 첫 부팅에서 dyld 캐시 못 찾음 (20:33)

증상: 설치 재부팅 두 번은 자동으로 잘 이어졌는데(20:14, 20:27), 설치된 OS 첫 부팅에서
커널 패닉. 로그: `libignition … dylib_cache: finding shared cache on cryptex` →
`vm_shared_region_start_address() failed` → launchd(pid1) 가 `/usr/lib/libSystem.B.dylib`
못 불러옴("no dyld cache") → launchd 종료 → 삼중 결함(`Double fault at …, @trap_native.c:168`).

기제 판정: libSystem.B.dylib 은 원래 파일로 존재하지 않고 dyld 공유 캐시 안에만 있다.
"no dyld cache" = 현재 CPU 서브타입에 맞는 공유 캐시를 커널이 매핑 못 함.
`vm_shared_region_start_address()` 는 그 서브타입용 공유 캐시가 매핑 안 됐을 때만 실패한다.
소노마(지원 맥이 전부 Haswell 이상)의 OS cryptex 는 **x86_64h**(Haswell 기능셋) dyld 캐시를
담는데, 순정 Penryn 은 baseline **x86_64** 서브타입으로 보여 캐시가 안 맞았다.

바이스(vise) 구조 판정 (팀 리드 질문 답): 일시적 부팅 선택 문제 아님(재부팅은 자동으로 잘 이어짐).
CPU 위장의 근본 한계도 아님 — 맥OS-on-QEMU 의 전형적 "CPUID 를 정확히 맞추는" 문제.
- Haswell 모델 → 커널 초기화에서 XCPM #DF (커널조차 못 뜸)
- Penryn 순정 → 커널·설치는 되나 x86_64h 캐시와 서브타입 불일치로 launchd 패닉
→ 실:  계열은 Penryn(XCPM 회피) + x86_64h 기능(avx2,bmi1,bmi2,fma,movbe,f16c,abm) 얹어
서브타입만 x86_64h 로. XCPM 은 기능이 아니라 계열로 켜지므로 안전.

원인 유도 결과(20:41): 그 CPU 로 재부팅하니 **cryptex 그래프트가 성공**했다:
`apfs_graft: successfully grafted … [os.clone.dmg]`, `authenticate_root_hash: … successfully
validated on-disk root hash`, `libignition: graft: pre-reboot os: grafted cryptex`. 즉 dyld 캐시
문제 해결됨. 로그의 "pre-reboot os" 는 맥OS 첫 부팅의 정상 흐름(cryptex 그래프트 후 의도적
재부팅). 그 재부팅 뒤 macintosh hd 를 다시 골라 실제 OS 부팅을 확인 중.

## 3차 벽과 부검 — 첫 부팅 또 launchd 패닉, 그리고 진짜 원인 (22:28~22:55)

증상: 22:28 설치 완료(선택기 세 번째가 "macOS Installer" -> "macintosh hd" 로 바뀜, MACVM-47).
첫 정식 부팅에서 지난번과 똑같이 `Library not loaded: /usr/lib/libSystem.B.dylib ...
(no such file, no dyld cache)` -> `pid 1 exited` (MACVM-48). 다음 부팅은 금지 표시(MACVM-49).
즉 2차에서 세운 "Penryn + x86_64h 기능 비트" 가설은 **기각**됐다.

부검(복구 환경 터미널에서 직접 측정):
- `sysctl machdep.cpu` 결과 AVX2·BMI1·BMI2 가 없다. `hw.optional.bmi1`=0, `hw.optional.bmi2`=0,
  `hw.optional.avx2_0`=0. `machdep.cpu.leaf7_features` 항목 자체가 없다.
  반면 FMA·MOVBE·POPCNT·SSE4.2·AVX1.0·F16C·LZCNT 는 전부 보인다.
  -> 없는 것만 골라 보면 전부 **CPUID 리프 7**에 있는 기능이다. 리프 1·확장 리프는 다 보인다.
- QEMU 탓이 아니다. 512바이트 부트섹터를 만들어(`/tmp/cpuidtest/boot.s`) 같은 CPU 옵션으로
  직접 재니 리프 7 EBX = **0x128** = BMI1(bit3)·AVX2(bit5)·BMI2(bit8) 정확히 켜져 있다.
  KVM 도 지원한다(`query-cpu-model-expansion` static host 로 확인).
- 원인은 XNU 소스에 있다. `osfmk/i386/cpuid.c`:

      if (info_p->cpuid_model >= CPUID_MODEL_IVYBRIDGE) {
          cpuid_fn(0x7, reg);
          info_p->cpuid_leaf7_features = quad(reg[ecx], reg[ebx]);

  **리프 7 은 CPU 모델 번호가 아이비브리지(0x3A) 이상일 때만 읽는다.** Penryn 은 모델 23(0x17)
  이라 커널이 리프 7 을 아예 쳐다보지 않는다. 기능 비트를 얹는 것 자체가 무의미했다.
- 그리고 x86_64h 판정은 같은 파일에서 리프1 부분집합(FMA·SSE4.2·MOVBE·POPCNT·AVX1.0) +
  확장 부분집합(LZCNT) + **리프7 부분집합(BMI1·AVX2·BMI2)** 이 모두 맞아야 한다.

사슬(이 하나로 지금까지 본 것 전부가 설명된다):
Penryn(모델 23) -> 리프7 안 읽음 -> x86_64h 판정 실패 -> 서브타입 x86_64 ->
소노마 OS cryptex 의 x86_64h 전용 dyld 공유 캐시를 못 매핑 -> launchd 가 libSystem 못 붊 ->
패닉 / 금지 표시.

사망 반경: "Penryn 계열" 셀이 죽었다. 맥OS-on-QEMU 우주는 안 죽었다 — 아래에서 살아났다.

## 원인 유도 재설계 — IvyBridge (22:55)

`-cpu IvyBridge`. 모델 번호 0x3A 는 리프 7 읽기 기준선을 딱 넘고, Haswell(0x3C) 미만이라
1차에서 커널을 죽인 XCPM 이중 결함은 그대로 피한다. 이 두 조건을 동시에 만족하는 모델은
사실상 아이비브리지 하나뿐이다.

    CPU_MODEL="IvyBridge"
    MY_OPTIONS="+avx2,+bmi1,+bmi2,+fma,+movbe,+abm,+f16c,+xsaveopt,check"

(아이비브리지에 SSE4.2·POPCNT·AVX·AES·XSAVE·FSGSBASE 는 이미 있다. 부트섹터로 미리 재니
리프7 EBX = 0x3a9 로 BMI1·AVX2·BMI2 다 들어간다.) 백업: `boot.sh.bak-penryn-x86_64h`.

결과: **재설치 없이 이미 깔린 설치본이 그대로 부팅됐다.** 22:58 Setup Assistant 도달
(MACVM-50). 메모리는 6144 그대로.

  권한이 있어야 하는데 터미널에 없다(조용히 실패하고 `-getremotelogin` 은 Off).
- 되는 방법:

      sudo launchctl enable system/com.openssh.sshd
      sudo launchctl load -w /System/Library/LaunchDaemons/ssh.plist

- 호스트 공개키(`/home/hoon/.ssh/macvm`)를 `~/.ssh/authorized_keys` 에 넣어 비번 없이 들어간다:

      ssh -p 2299 -i /home/hoon/.ssh/macvm belmont@127.0.0.1

CPU 고침이 맞았다는 게스트 안 증거:
- `hw.cpusubtype: 8` (= CPU_SUBTYPE_X86_64_H). 고치기 전에는 4 였다.
- `machdep.cpu.leaf7_features: RDWRFSGS BMI1 AVX2 SMEP BMI2 ERMS`. 고치기 전에는 이 항목 자체가 없었다.

온보딩은 사용자가 로그인 벽을 넘긴 뒤 내가 이어받았기 때문에 온보딩 단계별 스냅샷을

스냅샷은 기준선부터 뜬다.

| 번호 | 이름 | 시각 | 무엇을 담았나 |
|---|---|---|---|
| 01 | baseline-after-onboarding | 온보딩·주요 캡처가 다 끝난 뒤 | 기준선 |

차이 결과:

| 구간 | 바뀐 키 | 내용 |
|---|---|---|
| 02 → 03 (에이전트 작업 실행) | 6개, 전부 크로미움 쪽 | `https_upgrade_navigations`, `site_engagement`(newtab 점수), 방문한 사이트의 `app_banner` 항목. **`aside.*` 키는 하나도 안 바뀐다** — 작업 기록은 Preferences 가 아니라 데몬의 `state.db` 로 간다. |

**기본값일 때는 파일에 아예 없다가 건드리면 생기는 키**가 있다. 그래서 키 목록은 조작을

  (프로필 추가 → 그 프로필에서 온보딩이 다시 돈다).

## 13. 에이전트가 페이지를 어떻게 "보는가" (session_tabs.data)

`session_tabs` 표의 `data` 열이 답이다. 화면 그림이 아니라 **접근성 트리**를 담는다.
example.com 탭의 값 원문:

```json
{"title":"Example Domain","viewport":{"width":1440,"height":900},
 "snapshot":{"tree":"- heading \"Example Domain\" [level=1]\n- text: \"This domain is for use in documentation examples without needing permission. Avoid use in operations.\"\n- paragraph:\n  - link \"Learn more\" [ref=e1]","refs":{"e1": ...}}}
```

즉 제목 + 뷰포트 크기(1440×900 로 고정) + 요소를 `[ref=e1]` 처럼 번호 붙인 접근성 트리다.
이 번호로 클릭·입력 대상을 가리킨다. 토큰을 아끼는 방식이고, 우리 포크가 스크린샷을
많이 쓰는지 트리를 쓰는지 대조하면 검사표 ★6("토큰 2.3배↓")의 근거가 된다.

## 14. 민감정보 처리 확인
- 복사한 파일에 `credentials.json` · `passwords/` · `Cookies` · `Login Data` ·
  `Secure Preferences` 는 **0개**다(검색으로 확인).
- 로그 세 개(콘솔 2개 + 데몬)를 JWT·`Bearer`·`sk-` 모양으로 훑었고 **하나도 안 나왔다**.
- "token/secret/password" 이름이 걸린 키는 전부 무해했다: 토큰 **개수**(`token_usage`),
  창 위치 이름(`aside-account-password-popup`), 참/거짓 하나
  (`account_password_extension_available`).
- 다만 `Preferences` 사본에는 계정 표시 이름과 이메일이 평문으로 들어 있다(원본 파일 그대로).
  문서 본문에는 `<가림>` 으로 적었다. 이 폴더를 밖으로 옮길 일이 있으면 그 두 키를 지워라.

# 검사표 ★1·★3 실측 (한국어 원문 그대로)

# 설치된 파일 목록 (자세한 판은 `share/state/installed-inventory.md`)

## 앱 번들은 dmg 그대로다
`/Volumes/Aside Browser/Aside.app` 과 `/Applications/Aside.app` 의 모든 파일을 SHA-256 으로
떠서 맞춰 봤다. **파일 1,776개, 다른 파일 0개.** 설치할 때 격리 속성만 지웠고 내용은 그대로다.
즉 **업데이터는 앱 번들을 고치지 않는다.** 새 코드는 전부 프로필 폴더 안 컴포넌트로 들어간다.

## 판 번호가 세 갈래다 — 이미 906으로 올라가 있다

| 무엇 | 판 |
|---|---|
| 앱 번들 | 1.0.825.1 |
| 계정 설정 기기 줄에 보이는 값 | 1.26.824.2151 |
| **실제 돌아가는 컴포넌트** | **1.26.906.1714** (AsideDaemon·AsideAgentManager·AsidePasswordManager 셋 다) |
